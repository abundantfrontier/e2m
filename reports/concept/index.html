Concept paper

E2M: English to machine code

A research program for models that take an English specification of a function and emit executable machine code, judged by running that code, not by matching a compiler's text.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Living paper · Revision 3 · Last updated 14 November 2026 · First work product: the harness, sweep and scale-up report · Work so far is on one 24 GB RTX 3090 workstation · Code and data: github.com/abundantfrontier/e2m

Working paper. You may cite it; see How to cite. This page condenses the author's internal concept note (v0.1, 10 November 2026) and the design of the harness, data and evaluation. Sections marked planned describe intent, not results. Nothing here has been published.

Abstract

Code models are usually asked to write a high-level language, which a compiler then turns into machine code. E2M asks a different question: can a model go from an English specification, plus a function signature and calling convention, straight to machine code for a target ISA, without a human-visible source language in the loop? The output must pass tests, respect the ABI, stay memory-safe under the harness, and be competitive in size or speed with a compiler baseline. We treat the obvious control — the same base model writing C that gcc or clang compiles at -O2 — as the baseline to beat, not as a straw man. For general programming that baseline should dominate for the foreseeable future. The niches we take seriously are small hot kernels where search can beat the compiler, targets that have no compiler, and research on the compiler itself as a learned component. The working method is hybrid: the model proposes assembly, tools assemble and run it in an emulator, and only passing variants are kept. This paper states the goals, the case for and against skipping source, the approach, the safety rule that generated code is never run on the host CPU, the evaluation plan, and the open questions. The first experiments — an execution harness, compiler-parameter sweeps, and a 3,000-task scale-up from ExeBench — are reported separately.

1Goals and vision updated 11 Nov 2026

These are the long-range goals this research works toward. They are the reason for the design in the rest of the paper and for the experiments in the technical report.

1.1English in, machine code out

Given an English specification of a function, its signature and the calling convention, emit machine code — executable bytes, or assembly that a plain assembler turns into bytes — for a stated ISA. The first target is x86-64 System V. The output has to pass tests, restore callee-saved state, and stay competitive in size or speed.

1.2Correctness by execution

A candidate is correct if it assembles, runs in the harness, and matches the reference on the tests, including ABI checks. Matching a particular compiler's assembly text is not the goal. Weak tests will reward wrong code, so the suite has to be strong enough that a stub cannot pass.

1.3Beat, or honestly lose to, the compiler path

The control is the same base model writing C that gcc or clang compiles at -O2. Every claim about direct generation is compared with that path. A win on at least one axis — .text size, retired instructions or cycles, or "works with no toolchain on the target" — at equal pass rate is what would count as success.

1.4Model proposes, tools verify

The promising shape is a loop: sample candidates, assemble them, run tests in an emulator, and feed errors back. Supervised imitation of compiler output is a starting point. Beating the compiler on size or speed will need search or a reward that includes those measures.

1.5Safe to run on a shared machine

Generated machine code is executable content. Every run stays inside an emulator or a tightly limited sandbox. The host CPU is not the execution engine. Instruction caps, wall-time caps and a syscall deny-list are part of the design, not optional hardening.

1.6Self-hosted and modest hardware

Training and evaluation should run on one consumer GPU with open models and no subscription. The first prototype is sized for a 24 GB RTX 3090: a small code model with LoRA or QLoRA, a local assembler, and the harness.

1.7How the first work steps toward these goals updated 11 Nov 2026

We start at function level on x86-64, with tests and a C reference for each task, because that is the smallest setting in which execution, ABI checks and a compiler baseline can all be measured. If a model can emit leaf functions that pass the harness and come close to gcc -O2 on held-out tasks, later work can add search, other ISAs and whole programs. The first work product is the harness, the compiler-parameter sweep that turns many verified variants into training data, and a scale-up to 3,000 ExeBench tasks, reported in the technical report.

2Direct versus via source updated 11 Nov 2026

2.1Claim updated 11 Nov 2026

For general "write me a program" work, English to C to a compiler should dominate for the foreseeable future. E2M treats that path as the baseline to beat. Direct generation is worth studying in niches where a toolchain is missing, where search over machine code can beat the compiler on a small kernel, or where the compiler itself is the object of research. The method is the same in every case: the model proposes, and an assembler, an emulator and tests judge the proposal.

2.2The case for going through source updated 11 Nov 2026

This is the strong default, and the reasons are ordinary rather than ideological:

  • Data. Code models are trained on huge amounts of source — The Stack is 3 TB of permissively licensed code [6] — and on comparatively little assembly.
  • Review. A human can read C. Intent review happens at the C level, which is the cheapest place to catch an ambiguous specification.
  • Optimization for free. Mature compilers give semantics-preserving optimization, and CompCert shows that this can be proved for a C subset [16].
  • Retargeting. A new ISA is a compiler flag. Direct generation needs training data per ISA.
  • Length. Assembly is much longer than the source that produced it. In a five-function smoke test by the author (concept note, 10 November 2026), 449 characters of C became 1,429 to 3,588 characters of gcc assembly, depending on the -O level, and .text size varied 4.5× across those levels. Tokens are only a rough proxy, but the direction is clear.
  • Published neural compilation is mixed. Armengol-Estapé and O'Boyle (2021) call their C-to-x86 results "relatively weak" [7]. The 2025 CompilerEval (LaaC) paper reports basic ability but low compilation success rates [12]. NeuComBack reports 44% x86-64 correctness for a baseline workflow [11]. LLM Compiler reports 45% disassembly round trip and 14% exact match [8].

2.3The case for going direct updated 11 Nov 2026

  • No toolchain on the target. This matters for new or odd ISAs, firmware and embedded systems.
  • Search can beat the compiler on small kernels. STOKE matched or beat gcc -O3 and icc -O3 on small loop-free x86-64 kernels [14]. AlphaDev found sorting routines for 3 to 5 elements that were merged into LLVM libc++ [15]. SuperCoder reports an RL-tuned 7B model reaching 96.0% correctness and 1.47× average speedup over gcc -O3 on a benchmark of 8,072 assembly programs [13].
  • Joint trade-offs. A single model could trade size, speed and the specification together, instead of only through compiler flags.
  • It is a self-hosted research question that can be studied on one workstation.

2.4What would make the claim wrong updated 11 Nov 2026

  • If direct generation stays well behind the NL-to-C-to-gcc control on pass rate and never wins on size or speed, the program collapses to "use the compiler."
  • If supervised fine-tuning only imitates gcc, and search or reinforcement learning cannot be made to work on this hardware, there is no path past the imitation ceiling.
  • If specifications stay ambiguous and tests stay weak, passing the harness will not mean the code does what was asked.

The first LoRA run, now in progress, tests a slice of the first of these at small scale (report §7).

3Approach updated 11 Nov 2026

3.1Four routes updated 11 Nov 2026

Table 2. Candidate architectures. Every claim about A–C is compared with D.
RouteWhat it doesRole
A. Direct assemblySpecification and signature to x86-64 assembly text, then as, then testsSimplest; assembler gives cheap syntax feedback; long outputs and easy ABI mistakes
B. Via LLVM IRSpecification to LLVM IR, then llcTyped SSA and retargeting; Alive2 can check IR transformations [18]; starts to look like a compiler front end
C. Hybrid loopGenerate N candidates (A or B), assemble, run tests, feed errors back; optional superoptimization with equivalence checking; optional RL on correctness plus size or speedThe intended mature shape, following Self-Debug, compiler-feedback training, NeuComBack and SuperCoder [11, 13, 22, 23]
D. ControlSame base model, English to C to gcc or clang -O2, scored on the same harnessThe baseline every other route must beat or lose to honestly

The recommendation is to build D and A on the same harness first, then add the C loop. Route B is reserved for the case where A struggles with the ABI or with retargeting.

3.2Data updated 11 Nov 2026

No public dataset pairs English specifications with machine code, so the English side has to be synthesized. The plan, now partly executed (report §4–5), is:

  1. Seed functions from ExeBench executable splits [19] and, if they pass the filters, AnghaBench [20]. HumanEval-C and MBPP-C style tasks are held out of training.
  2. Specifications written by a local open model from the C, keeping the signature. Expected outputs always come from running the reference, never from the model. Tasks where a stub such as return 0 would pass are dropped.
  3. A compiler sweep over gcc, clang and, where a Rust reference exists, rustc, across optimization levels, -march and CPU, feature bundles and codegen toggles, with optional random LLVM pass orderings. Variants are executed in the harness, deduplicated by SHA-256 of the function bytes, and ranked by size and instruction count to build an SFT set and preference pairs.

Licensing of the underlying GitHub-derived functions has to be checked before any release. The Stack is filtered for permissive licenses [6]; ExeBench and AnghaBench are not, function by function, in the same way.

3.3First prototype updated 11 Nov 2026

The first training run is a LoRA fine-tune of a small open code model — starting with Qwen2.5-Coder-1.5B [25], with Qwen3-1.7B as a cached fallback — from English specification and signature to assembly text. That text is assembled and run through the harness; anything that does not assemble is a failure. The run is scored on pass@1 and pass@5, and on size and instruction count against gcc -O2, on a held-out HumanEval and MBPP style set, next to two baselines: the base model with no LoRA, and route D. A 7B QLoRA [26] is the next increment if the 1.5B run is promising and memory allows. Sequence length is the binding constraint, because assembly is long.

4Related work updated 11 Nov 2026

This is a short orientation, not a survey. Numbers below are taken from the cited abstracts or from the concept note, which opened those papers on 10 November 2026. They are not re-scored here. Compare numbers only within one paper: evaluation setups differ.

4.1Natural language to code updated 11 Nov 2026

Codex and HumanEval showed that repeated sampling plus tests is a strong lever: 28.8% pass@1, and 70.2% with 100 samples per problem [1]. MBPP has 974 entry-level Python tasks; a 137B few-shot model solved 59.6% [2]. AlphaCode reached the top 54.3% on average in Codeforces contests with 5,000-plus participants by sampling at large scale, filtering and clustering [3]. StarCoder, trained on The Stack, reached about 40% pass@1 on HumanEval when prompted [4]. We do not quote later leaderboard numbers that we have not opened. EvalPlus showed that HumanEval-style benchmarks have false positives and added many more tests [5]. Multilingual ports (MultiPL-E, HumanEval-X, MBXP) give English specifications with tests in C-family languages [21, 27]. The implication for E2M is twofold: natural language to a high-level language is solved well enough at small scale that skipping it needs a stated reason (§2), and the same sample-and-filter loop transfers directly, because assembly can be tested by running it.

4.2Neural compilation and assembly generation updated 11 Nov 2026

Armengol-Estapé and O'Boyle ran an early Transformer experiment on C to x86 and called the results relatively weak, with data and code released [7]. Meta's LLM Compiler continued-trains Code Llama on 546B tokens of LLVM IR and assembly (7B and 13B, under a bespoke commercial license); fine-tuned variants reach 77% of an autotuner's code-size gains, 45% disassembly round trip and 14% exact match [8]. Related work trains models to predict optimization passes or to use compiler-generated feedback [9, 23]. LEGO-Compiler decomposes programs into blocks, checks each with external tests, and reports over 99% on ExeBench and 97.9% on AnsiBench — with heavy scaffolding [10]. QiMeng-NeuComBack is an IR-to-assembly benchmark (200 ExeBench cases plus 151 TSVC cases) on which a self-evolving prompt method raises x86-64 correctness from 44% to 64% and aarch64 from 36% to 58%; 14 of 16 correct x86-64 programs beat clang -O3 [11]. CompilerEval (LaaC) finds that mainstream models have a basic ability to emit assembly but low success rates, and argues that targeted training and prompting help [12]. IRCoder and TransCoder-IR show that training on compiler IR helps multilingual code models and translation [28, 29]. The pattern is consistent: models can produce assembly, but reliable results come from scaffolding (decompose, test, retry), not from one-shot generation.

4.3Neural decompilation updated 11 Nov 2026

The inverse problem is a source of methods and of (source, binary) pairs. LLM4Decompile (open 1.3B to 33B models) reports large relative gains in re-executability over GPT-4o and Ghidra on HumanEval and ExeBench [30]. Nova is an assembly-specialized model with hierarchical attention, motivated by assembly's low information density and by optimization diversity [31]. SLaDe is a small Transformer decompiler evaluated on more than 4,000 ExeBench functions on two ISAs and two -O levels, and reports up to 6× the accuracy of Ghidra [32]. Guess & Sketch guides transpilation with a language model and a symbolic repair step [33]. LLM4Decompile and Nova report different numbers for the same model family because their evaluation setups differ. For E2M, the useful residue is how to build paired data at scale and how to tokenise assembly.

4.4Superoptimization updated 11 Nov 2026

STOKE used MCMC search over loop-free x86-64, with correctness and speed in the cost function and with equivalence checking, and matched or beat gcc -O3 and icc -O3, sometimes expert assembly [14]. Souper is a synthesizing superoptimizer for LLVM IR that finds missed peephole optimizations [34]. A 2016 paper learned a neural proposal distribution for that kind of search [35]. AlphaDev trained reinforcement learning on an "AssemblyGame" and produced sort-3, sort-4 and sort-5 routines that were adopted into LLVM libc++; the paper reports up to 70% faster for short sequences and about 1.7% for sequences over 250,000 elements [15]. SuperCoder treats language models as assembly superoptimizers, with an RL reward of correctness plus speed; Qwen2.5-Coder-7B-Instruct went from 61.4% correctness and 1.10× speedup to 96.0% and 1.47×, averaged over gcc -O3, on 8,072 programs, against a strongest zero-shot baseline in that paper of 51.5% test pass and 1.43× [13]. LLM-Vectorizer writes SIMD code with test feedback (1.1× to 9.4× speedups) and used Alive2 to verify 38.2% of vectorizations as correct on TSVC [36]. Source-level relatives include PIE (performance-improving edits) and Supersonic [37, 38]. This is the strongest evidence for E2M's value: a model proposes, tools verify, on small kernels.

4.5Program synthesis and verified compilation updated 11 Nov 2026

CompCert is a machine-checked proof that compiled code preserves C semantics [16]. That is the gold standard, but it is a proof about a compiler, not about a neural model. Translation validation — do not prove the compiler, validate each run — is the right pattern for a neural compiler [17]. Alive2 does bounded translation validation for LLVM IR with an SMT solver and found 47 bugs in LLVM's own tests, 28 of them later fixed [18]. STOKE includes x86-64 equivalence checking that can go from tests to bounded checks to full verification on loop-free code [14]. Tests give confidence; translation validation gives guarantees for a subset (loop-free or bounded loops). E2M should report which tier each result reached: tests only, fuzzed, or proved. The first prototype reports only the tests-only tier.

4.6Datasets updated 11 Nov 2026

ExeBench has 4.5M compilable and 700k executable real C functions with I/O examples; the v1.01 splits include train_real_simple_io (43.8k), synthetic I/O splits, and test_real (2.1k) [19]. AnghaBench has over a million compilable C functions mined from public repositories [20]. ComPile is a 182B-token LLVM-IR dataset from production Rust, Swift, Julia and C/C++ [39]. The Stack and The Stack v2 supply permissively licensed source [6, 40]. HumanEval-X, HumanEval-Decompile, MBPP, MBXP, MultiPL-E and EvalPlus supply specifications and tests for evaluation [1, 2, 5, 21, 27, 30]. SuperCoder's 8,072-program set is the nearest ready-made assembly optimization benchmark; its provenance and license should be checked before use. The gap is the same in all of these: none pair English specifications with machine code.

5Safety updated 11 Nov 2026

Generated machine code is never executed on the host CPU. The only execution path is an emulator (Unicorn by default [41], QEMU user-mode as an optional second backend [42]) or, for a stretch whole-program runner, a child process with resource limits and a seccomp allow-list. That rule is part of the research design, not only a property of one machine.

The function-level harness maps code, stack and data pages, pushes a sentinel return address, and stops when ret hits it. It enforces an instruction cap and a wall-time cap, hooks and rejects syscall, int and sysenter, and treats unmapped or permission faults as failures. Callee-saved registers (rbx, rbp, r12–r15, rsp) must be restored, and the stack must be 16-byte aligned at calls. Out-of-bounds writes are flagged through memory hooks; control flow must not jump outside the function, modify its own code, or take an indirect call to an unmapped address. A crash report (fault address, rip, a disassembly window, registers) is recorded; an exception must not escape the harness.

Unicorn cannot enforce sub-page bounds faithfully, so buffers use page granularity and a guard page; an off-by-one that stays on the same page can still succeed. That is a known limitation, not a solved problem. QEMU user-mode is used where Unicorn cannot run a variant faithfully (in particular AVX2, FMA and non-destructive VEX). Native execution under seccomp and ptrace is noted as a possible option and is not the default backend. For any future native path, the same isolation rules would apply.

6Evaluation updated 11 Nov 2026

Functional correctness is pass@k with the unbiased estimator from the Codex paper [1]: sample n ≥ k, count correct c, and report at least pass@1 and pass@5 (the concept note also asked for pass@10). Anything that does not assemble is a failure. Metrics are reported against gcc -O2 as the size and speed reference, and also against -Os for size:

  • Assembles, and passes the tests, including ABI checks.
  • Code size in .text bytes, relative to the compiler baseline.
  • Dynamic instruction count in the emulator, summed over the task's tests. This is a retire-count proxy, not perf cycles; native cycles are future work.
  • Failure categories: does not assemble, crash, wrong answer, timeout, ABI violation, unsupported instruction.

The strongest control is route D on the same held-out set. HumanEval-C and MBPP-C style tasks are held out of training and decontaminated by name and by normalized body. A passing test on a bad specification means nothing, so a sample of specifications should be checked by a person. Differential fuzzing against the reference, with more inputs than the training tests, follows the EvalPlus lesson [5]. Equivalence checking (STOKE-style or Alive2 on IR) is the strongest tier and is not in the first prototype; when it is added, each pass should be labeled tests-only, fuzzed, or proved.

8Open questions updated 11 Nov 2026

  1. Does direct generation ever beat the compiler path? On pass rate, on size, on speed, or only on targets with no compiler?
  2. Imitation ceiling. Supervised training on compiler output teaches the model to imitate gcc. What reward, search or verification is enough to go past that, on one 24 GB GPU?
  3. Specification adequacy. How should we detect a specification that omits behavior the tests do not cover, other than by occasional human review?
  4. Undefined behavior in C seeds. A compiler may exploit it, so the "right" assembly is not unique. Sanitizer-clean seeds are a start; they are not a proof.
  5. ABI and calling convention. Tests on a single harness can miss clobbers and alignment bugs that surface on a different caller.
  6. Long functions. Assembly is long. Is block decomposition (as in LEGO-Compiler) necessary, or will short leaf functions be enough to learn a useful prior?
  7. Emulator fidelity. Unicorn 2.1.4 cannot run AVX2, FMA or non-destructive VEX faithfully. QEMU is slower. How should a training set weigh coverage against throughput?
  8. Equivalence versus tests. When is "passed the tests" enough, and when should a result be withheld until translation validation?
  9. Contamination and licensing. Held-out HumanEval and MBPP tasks may already be in the base model's pretraining. ExeBench and AnghaBench come from GitHub; what can be released?
  10. Is E2M a tool or a probe? If it is only a probe, a clear loss to the C baseline is still a result. If it is a tool, that loss is a stop.
