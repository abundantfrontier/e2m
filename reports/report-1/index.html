Harness, compiler-sweep data, and scale-up

Technical report 1 of the E2M program: an execution harness for model-generated x86-64, compiler-parameter sweeps that turn verified variants into training data, and a 3,000-task scale-up from ExeBench.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Living paper · Revision 3 · Last updated 14 November 2026 · Companion to the E2M concept paper · All results are from one 24 GB RTX 3090 workstation · Code and data: github.com/abundantfrontier/e2m

Working paper. You may cite it; see How to cite. Numbers are copied from STATUS.md, data/SWEEP_REPORT.md and data/scaled/SWEEP_REPORT.md on the 3090; nothing here is rounded or re-scored. The first LoRA run is marked in progress and has no results yet.

Abstract

E2M is a program for models that emit machine code from an English specification. Before any training, we needed a way to assemble, run and score generated x86-64 without executing it on the host CPU. This report describes that harness, a compiler-parameter sweep that turns many verified variants of the same function into supervised and preference data, and a scale-up from ExeBench. The harness is a Python package that assembles AT&T, Intel or hex, runs the function under Unicorn with the System V ABI, instruction and time caps, syscall hooks and callee-saved-register checks, and scores pass@k plus size and retired-instruction counts against gcc -O2. A 98-test suite passed; a 10,000-input fuzz run had 0 harness crashes and 0 hangs, at 3,404 runs/s. All 20 starter tasks passed at gcc -O0, -O2 and -Os. A full sweep of those 20 tasks over gcc, clang, rustc and random LLVM pipelines recorded 67,640 configs, of which 61,743 passed, collapsing to 721 unique variants, 60 SFT rows and 434 preference pairs. Optimization level was the diversity knob (0.952 of held-fixed groups). The largest loss was Unicorn 2.1.4, which could not run 3,563 AVX2, FMA or non-destructive VEX variants. We then filtered 42,769 ExeBench train_real_simple_io rows down to 7,079 functions the harness can run, and used a local qwen3:14b model to write English specifications for 3,000 of them (3,137 s of model time). A reduced gcc and clang sweep of those tasks ran 432,000 configs, of which 389,637 passed, giving 20,123 unique variants, 9,000 SFT rows and 44,432 preference pairs. QEMU 8.2 user-mode was added as an optional second emulator (Unicorn stays the default; 1,399 vs 272 runs/s on a microbenchmark) and recovered 1,212 of 1,542 starter-sweep AVX drops (78.6%). A first LoRA training run on the scaled data, with a held-out HumanEval and MBPP style set and an NL-to-C-to-gcc -O2 control, is in progress; this report does not invent numbers for it.

1Goals recap updated 11 Nov 2026

The long-range goal, set out in the concept paper (§1), is a model that takes an English specification of a function, plus its signature and calling convention, and emits machine code that passes tests, respects the ABI, and is competitive with a compiler baseline. The control is the same base model writing C that gcc compiles at -O2. Generated code is never run on the host CPU.

This report is the first work product on that path. It covers the harness that makes execution and scoring possible, the compiler sweeps that produce training data, the ExeBench scale-up that takes the task set from 20 functions to 3,000, and the choice of a second emulator so vectorized variants are not all dropped. The first LoRA run is underway and is recorded in §7 as in progress, with the results table left pending.

2Execution harness updated 11 Nov 2026

2.1What was built updated 11 Nov 2026

A Python 3.12 package e2m assembles model-generated x86-64, runs it inside Unicorn (never on the host CPU), and scores it against JSONL tasks. The v0 work was CPU-only, in a venv at .venv (CPython 3.12.16 via uv), with unicorn 2.1.4, capstone 5.0.9, pyelftools 0.33 and pytest 9.2. No GPU, no sudo and no apt were used for this stage.

Table 1. Harness pieces.
PiecePathRole
Assemblee2m/harness/assemble.pyGNU as/ld; AT&T, Intel, hex; reject externals and sections other than .text/.rodata
Emulatee2m/harness/emu.pyUnicorn x86-64 SysV, sentinel ret, limits, ABI checks, crash reports; later, an optional QEMU backend (§6)
Taskse2m/harness/tasks.py, tasks/starter.jsonl20 hand-written functions plus a gcc baseline
Scorepython -m e2m.scorepass@k, size, instruction counts vs gcc -O2, JSON and Markdown
Fuzzpython -m e2m.fuzzRandom and mutated blobs, multiprocessing, per-batch timeout
Sandboxe2m/harness/sandbox.pyStretch: fork, rlimits, and seccomp allowing write, exit and exit_group

The emulator maps code RX, a stack RW with guard gaps, and input buffers for pointer arguments. Arguments are placed in rdi, rsi, rdx, rcx, r8, r9 and, for doubles, xmm0–7. A sentinel return address is pushed; execution stops when ret hits it. An instruction-count limit and a wall timeout are enforced. Hooks fail syscall, int and sysenter. Unmapped and permission faults are caught. Callee-saved registers (rbx, rbp, r12–r15, rsp) must be preserved, and the stack must be 16-byte aligned at calls. On a fault the harness returns a structured report (fault address, rip, a Capstone disassembly window, registers) and does not let an exception escape.

2.2Tests and the gcc baseline updated 11 Nov 2026

pytest ran 98 tests and all passed. Coverage included 20 starter tasks times gcc -O0 / -O2 / -Os (60 baseline runs, all pass); assembly of AT&T, Intel, hex and .rodata strings, with rejection of call foo and .data; emulation of addition, doubles, in-place reverse, blocked syscall/int/sysenter, an instruction cap on jmp $, callee-saved canaries and 16-byte call alignment; a score CLI check (pass@1 = 1.0 on a hex add_i64 candidate, and gcc -O2 candidates scoring pass@1 = 1.000 on all 20 tasks); and a sandbox check in which a write+exit program printed hello\n and exited 0, while mmap (not allowed) was killed.

2.3Fuzz updated 11 Nov 2026

python -m e2m.fuzz --n 10000 ran with multiprocessing, 50-input batches, a 4k instruction cap, a 50 ms timeout, and ABI checks off. It completed 10,000 inputs with 0 harness crashes and 0 hangs, at 3,404 runs/s (2.94 s elapsed). The parent RSS delta was about 3.6 MiB. The typical histogram was: unmapped 5,850, invalid_insn 1,512, ok 654, int 518, no_return 502, io 387, syscall 199, sysenter 190, assemble_error 143, prot 45. An in-process RSS check (200 runs in the pytest worker) stayed under a 64 MiB slop budget.

2.4Stretch sandbox updated 11 Nov 2026

The whole-program sandbox was implemented, not skipped. A child process maps anonymous memory RW, copies bytes, and mprotects them RX (W^X; Ubuntu 26.04 rejects RWX). Resource limits are CPU 1 s, address space 512 MiB (set above the Python child's existing VSZ), NOFILE 16, NPROC 8 and CORE 0. It attempts unshare(CLONE_NEWUSER|CLONE_NEWNET), then prctl(PR_SET_NO_NEW_PRIVS) and a libseccomp allow-list of write=1, exit=60 and exit_group=231. Entry is via CFUNCTYPE; there is no execve of a host binary, so the guest cannot spawn /bin/sh. libseccomp.so.2 was already present as a runtime library. The Python runtime is still mapped in the child; seccomp is the real fence, and a guest that jumps into libc still cannot make a disallowed syscall.

3Starter-task compiler sweep updated 11 Nov 2026

The point of the sweep is to turn each task (English specification, tests, C or Rust reference) into many verified machine-code variants, then deduplicate and rank them for training. Generated code ran only inside Unicorn. The work was CPU-only, dated 10 November 2026 in STATUS.md.

3.1Grid and tools updated 11 Nov 2026

A Rust reference was added for each of the 20 starter tasks: #![no_std], panic=abort, #[no_mangle] pub extern "C" fn with the same SysV signature, wrapping arithmetic, inline idiv for remainder, and volatile byte loads so LLVM does not emit strlen, memcpy or memcmp. Canonical rustc -C opt-level=2 -C target-cpu=x86-64 -C overflow-checks=off passed every starter test through the harness.

The cartesian grid (e2m/data/grid.py, 16 worker processes, resumable from a gitignored data/sweep-cache.jsonl) was:

  • gcc / clang: -O0,-O1,-O2,-O3,-Os,-Oz × march x86-64, x86-64-v2, x86-64-v3, znver3 × feature bundles (default, -mno-avx -mno-avx2, 128-bit AVX without FMA, plain -mavx2, SSE2-only) × toggles (unroll on/off, vectorize on/off, inline-insns 1 and 1000, no alignment).
  • rustc: opt-level 0, 1, 2, 3, s, z × the same four CPUs × feature bundles (+avx2, -avx,-avx2, +avx2,-fma, SSE2-only, default) × overflow-checks off/on × LLVM args (unroll threshold, inline threshold, vectorize-loops off).
  • llvm-opt (when clang, opt and llc exist): unoptimized IR, then default<O0>…default<O3> and N random new-PM pass pipelines. LLVM 23 has no -Os/-Oz and no default<Os>; size rows are default<O2> plus optsize / minsize function attributes.

Fixed C flags on every gcc/clang compile: -fno-asynchronous-unwind-tables -fno-unwind-tables -fcf-protection=none -fno-stack-protector -fno-pic -ffreestanding -m64. Tool versions: gcc 15.2.0 (/usr/bin/gcc); clang, opt and llc, LLVM 23.1.5 under tools; rustc 1.99.1 (~/.cargo/bin/rustc).

3.2Results updated 11 Nov 2026

The full grid finished in about 5 minutes on 16 workers. It recorded 67,640 configs. The current grid is 67,560; 80 extra llvm-opt rows are an earlier llc -O pairing of the same random pipelines (seeds 6–9) and were kept because they passed. goal=default is gcc -O2 -march=x86-64 on all 20 tasks. All 721 unique variants were assembled again from the stored assembly and passed that task's tests under Unicorn; the SHA-256 of the function bytes matched the dataset. Examples of the size and instruction-count spread: add_i64 is 5–25 bytes and 10–45 retired instructions; sum_to is 22–188 bytes and 32–1,874 instructions. Per-task min/median/max figures are in data/SWEEP_REPORT.md.

Unicorn 2.1.4 rejects 256-bit YMM, FMA and vpbroadcast*. It also ignores VEX.vvvv and computes dest = dest OP rm, so non-destructive AVX is dropped. SSE and BMI2 are kept. Destructive 128-bit AVX (for example vpaddq xmm1, xmm1, xmm0) is kept. The 54 external_reloc failures are gcc sum_to with AVX2 emitting .set .LC2, .LC0+24 inside a 32-byte pool; the extractor does not follow .set. That pool is YMM-sized and would have been dropped as unsupported_insn anyway. pytest after the sweep code landed still passed.

Dedup is by SHA-256 of the linked .text bytes of the extracted function. goal=size prefers fewer bytes, then fewer instructions; goal=speed prefers fewer instructions, then fewer bytes; goal=default is the plain gcc -O2 -march=x86-64 variant when it passed. Preference pairs sample the ranked list (best against a spread of worse unique variants), capped at 8 per task per goal. A unique SHA-256 that two compilers both emit counts once in the total and once in each compiler's unique column.

4Task scale-up from ExeBench updated 11 Nov 2026

The starter set is too small to train on. The scale-up, dated 11 November 2026 in STATUS.md, pulls real functions, keeps only those the harness can run, and asks a local model to write an English specification for each. The GPU was used only through local Ollama (qwen3:14b). Generated and compiled task code ran in Unicorn or QEMU user-mode, never on the host CPU.

4.2Filters and task counts updated 11 Nov 2026

tasks/scaled.jsonl holds 3,000 verified tasks. 912 of the 3,000 have a for or while in the C. The pipeline (resumable, 16 compile/verify workers) was: cheap-filter 42,769 ExeBench rows → 16,380 cheap-kept → 9,812 compile-as-leaf → 7,079 pass -O0/-O2 plus the stub filter. The LLM then wrote specifications for the first 3,000. Expected outputs always come from gcc -O0 through the harness. Tests must also pass gcc -O2 with the same outputs. Stubs (return 0, return arg0) that pass the tests drop the task. Functions whose names match HumanEval or MBPP were held out (1,244 rows) so those benchmarks stay clean for evaluation.

4.3Specification synthesis updated 11 Nov 2026

Ollama qwen3:14b was called with think: false and JSON format. One call per task asked for an English specification, a short user-style prompt, and an adequacy score from 1 to 5 (drop if 1). Model time was 3,137 s (about 52 minutes) for 3,000 specifications. Four replies were malformed JSON or code-like, across both runs. No qwen3:8b fallback was needed except for those four. Expected outputs were never taken from the model.

6AVX-capable emulator updated 11 Nov 2026

Unicorn 2.1.4 cannot run AVX2, FMA, YMM, or non-destructive VEX (VEX.vvvv). That is why 3,563 starter variants and 34,520 scaled builds were dropped. Options considered:

Table 13. Emulator options.
optionverdict
Newer UnicornNo release supports AVX2. Upstream TCG is still QEMU 5.x. An AVX/AVX2 port exists as a commit, not a release.
Intel SDE 10.xFree under the Intel Simplified Software License (2023-08-23). User-level use is allowed. Redistribution of the emulator is forbidden (no redist.txt for SDE itself). Not used.
Native subprocess + seccomp/ptraceAllowed only as a note. Not the default backend.
QEMU 8.2 user-mode TCGChosen. qemu-x86_64 -cpu max runs AVX2/FMA. A tiny ET_EXEC ELF wrapper dumps the result via write+exit. Guest syscalls are pre-scanned. rlimits and a wall timeout sit on the QEMU process.

The default remains Unicorn. QEMU is selected with emulate(..., backend="qemu") or E2M_EMU_BACKEND=qemu. The binary is QEMU 8.2.2, extracted as a static qemu-x86_64 from the Ubuntu qemu-user-static package into tools/qemu.

Throughput on add_i64 -O2 (40 runs): Unicorn 1,399 runs/s, QEMU 272 runs/s. Starter gcc -O2 tasks all pass on QEMU. An -O3 -march=x86-64-v3 -mavx2 array_sum_i32 with n=16 is unsupported_insn / invalid_insn on Unicorn and returns 120 on QEMU.

A re-verify of starter-sweep unsupported_insn rows (gcc and clang only) covered 1,542 unique (task, flags) configs, of which 1,212 pass on QEMU (78.6%). The 330 failures are QEMU timeouts or SIGSEGV on short-array AVX over-reads (dot_f64 tests have n≤3; a YMM load reads 32 bytes). rustc AVX drops were not rebuilt. The first LoRA brief includes a harness buffer-padding fix for those 330 cases and a re-check of the scaled 34,520 unsupported_insn rows; those results are not yet in this report.

7First LoRA run 1.5B and 7B done updated 11 Nov 2026

1.5B and 7B QLoRA results in. The 1.5B LoRA and baselines are reported in §7.2 from STATUS.md. The 7B QLoRA scored 5 of 78 held-out tasks (pass@1 0.064), up from 2 for the 1.5B, still far below the 0.397 of the NL-to-C-to-gcc control. The 7B base-model baseline was cut off at 28 of 78 tasks and is not reported.

7.1Method updated 11 Nov 2026

The brief has three parts, in order:

  1. Harness fix and QEMU re-check (CPU). Pad short-array buffers so the 330 AVX over-reads described in §6 are no longer false crashes, while out-of-bounds writes are still detected. Re-verify every scaled-sweep config that failed with unsupported_insn (about 34.5k, 34,520 in Table 12) on the QEMU backend, then merge, re-deduplicate and re-rank data/scaled/.
  2. Held-out eval set. Build eval/heldout.jsonl with at least 60 problems from HumanEval and MBPP (for example via MultiPL-E prompts and tests) that fit the harness. Each item gets an English specification, a SysV signature, a C reference, tests, and verification through the harness at gcc -O0 and -O2. None may appear in tasks/scaled.jsonl (name and normalized-body near-duplicate check). This set is held out of training.
  3. First LoRA. Base model: Qwen2.5-Coder-1.5B-Instruct, falling back to the cached Qwen3-1.7B if needed. LoRA (bf16, PEFT/TRL or Hugging Face Trainer) on data/scaled/sft.jsonl with goal=default: the input is the English specification, signature and goal; the output is assembly text for the function body. A 3% validation split is held out by task. Model output is assembled with GNU as or llvm-mc and run through the harness; anything that does not assemble is a failure. Metrics: pass@1 (greedy) and pass@5 (sampling, T=0.8), plus bytes and dynamic instruction count against gcc -O2 for passing solutions, and a breakdown of failures (does not assemble, crash, wrong answer, timeout, ABI violation).

Baselines on the held-out set, same metrics: the base model without LoRA, and the NL-to-C-to-gcc -O2 control (the same model writes C from the specification, compiled with gcc -O2, run through the harness). If time and memory allow after the 1.5B results, a 7B QLoRA (Qwen2.5-Coder-7B-Instruct, 4-bit) may be run with the same evaluation. The session budget is about 10 hours of GPU time. Checkpoints go under runs/lora1/.

8Limitations updated 11 Nov 2026

  • The Unicorn path is function-level only. There is no libc, no FILE*, and no SIMD beyond SSE2 in the original v0 starters, other than what later sweeps emitted and QEMU can now run.
  • Unicorn cannot enforce sub-page bounds. Buffers are page-granularity with a right-align trick and a guard page. An off-by-one inside the same page still succeeds. The 330 short-array AVX failures on QEMU are the same family of problem; a padding fix is in the in-progress brief and is not claimed as done here.
  • Stack arguments beyond the six integer and eight SSE registers are not implemented.
  • Instruction counts are emulator retire counts, not perf cycles. Native cycles remain future work.
  • Equivalence checking (STOKE / Alive2) is not in this version. Every pass in this report is tests-only.
  • The stretch sandbox still has the Python runtime mapped in the child. Seccomp is the fence.
  • AnghaBench did not contribute tasks after the leaf and struct filter. Volume came from ExeBench only.
  • Specifications were written by qwen3:14b. Four replies were malformed and were retried. A systematic human review of specification adequacy has not been done. Expected outputs do not come from the model, but a fluent specification can still omit behavior the tests miss.
  • ExeBench and AnghaBench come from GitHub. Licenses have not been cleared for a public release of the derived tasks.
  • Supervised data is compiler output. A model trained on it may imitate gcc rather than beat it. Preference pairs exist for a later stage; they have not been used yet.

9Next steps updated 14 Nov 2026

  1. Repair loop and rejection sampling: done as a first pass. Results are in technical report 2.
  2. Run rejection sampling over held-out-like tasks (see §7.2).
  3. Read the 1.5B result against the NL-to-C-to-gcc control. If it is close on pass@k, or ahead on size at equal pass rate, consider the 7B QLoRA. If it is far behind, the interesting next step is the repair loop (best-of-n, test feedback), not a larger imitation run.
  4. Human check of a sample of specifications, as the concept paper asked, because a passing test on a bad specification is not a result.
  5. Past imitation: train on the preference pairs, then a correctness-plus-size-or-speed reward, with equivalence checking where the code is loop-free or bounded.
  6. aarch64 and whole programs, using the QEMU user-mode path already in the harness.

10Reproducibility updated 11 Nov 2026

All of this work lives in a local repository on the 3090 at ~/e2m, branch main. Nothing has been pushed, and nothing here is public. The environment is a user-level CPython 3.12.16 venv via uv, on one 24 GB RTX 3090 workstation. Tool versions used in the sweeps: gcc 15.2.0, LLVM 23.1.5 (clang, opt, llc under tools), rustc 1.99.1, unicorn 2.1.4, capstone 5.0.9, a static qemu-x86_64 8.2.2 under tools/qemu, and Ollama qwen3:14b for specification writing only.

Commands that reproduce the reported stages, from STATUS.md:

source .venv/bin/activate
python -m pytest
python -m e2m.fuzz --n 10000
python -m e2m.score --tasks tasks/starter.jsonl --candidates tasks/gcc-O2-cands.jsonl --baseline O2
python -m e2m.data.sweep --tasks tasks/starter.jsonl --out data --jobs 16 --llvm-seeds 12
python -m e2m.scale --target 3000 --jobs 16
python -m e2m.data.sweep --tasks tasks/scaled.jsonl --out data/scaled \
    --compilers gcc,clang --grid reduced --jobs 16 --llvm-seeds 0
python -m e2m.scale --avx-recover --jobs 8

Sweep caches (sweep-cache.jsonl) are gitignored; the JSONL datasets and the Markdown reports are the citable local artifacts for the numbers in this paper. A later LoRA run will add its own reproduction notes; they are not available yet.
