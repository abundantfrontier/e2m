Technical report · fourth work product

A stable preference run, and a model that writes good C but loses it in assembly

Technical report 4 of the E2M program: DPO from lora2 again, this time with a supervised term, goal-consistent prompts and a collapse guard; and a 7B QLoRA that writes the C function first and then the assembly, with both halves scored on the same tests.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Numbers are copied from runs/round3/SUMMARY.md, runs/round3/RESULTS.json, logs/round3.done, the training files under runs/dpo2 and runs/c-then-asm, runs/loop-c-then-asm-heldout/summary.json, and (for older rows) runs/round2b, runs/round2, STATUS.md and Report 3, all on the 3090; nothing here is re-scored. Abstract

Report 3 found that DPO from lora2 collapsed and that every assembly model scores far lower on held-out tasks than the NL-to-C-to-gcc control. Round 3 tested one fix for each. Part A repeated DPO from lora2 with a supervised (RPO-style) term of weight 1.0 on the chosen response, beta 0.2, learning rate 5e-6, 1,500 steps, each pair's real goal in the prompt, and a guard that checked every 250 steps how many of 30 fixed validation tasks still assemble. It did not collapse: the guard read 29, 25, 25, 28, 27, 26 and 26 of 30 against a stop threshold of 0.773, and the final model scores 26/90 greedy and 43/90 at pass@5 on validation and 2/78 on held-out (both measures). That is below lora2 (38/90 and 45/90; 4/78 and 5/78), so the held-out repair loop was skipped by its gate. The supervised term prevents the collapse, but preference training on these pairs does not yet help. Part B trained a 7B QLoRA to write the C function, then the assembly. Its assembly half scores 40/90 and 54/90 on validation and 7/78 and 9/78 on held-out, close to qlora7b-v2 (41/90 and 52/90; 5/78 and 12/78). Its C half, compiled by gcc -O2 in the same harness, passes 63/90 on validation and 48/78 on held-out, against 31/78 greedy for the untrained 1.5B C control. On held-out, 42 tasks have passing C and failing assembly, and one has the reverse. The fine-tuned model's C is strong, and the loss is in its own lowering to assembly. A held-out repair loop for the new model stopped at its 10-hour cap after 59 of 78 tasks, passing 15 of those 59. Round 3 used 18.60 of its 30 GPU hours.

1Goals recap updated 18 Nov 2026

Report 3 ended with two open problems. First, DPO from lora2 reached a pair accuracy of 0.902 while its generation collapsed (83 of 90 validation outputs did not assemble), and Report 3 listed untested causes, among them the missing supervised term, the mismatch between pair goals and the Goal: default prompt, and aggressive settings. Second, the best assembly models pass 5 to 12 of the 78 held-out tasks, while the same family of model asked for C and compiled by gcc passes 31/78 greedy and 44/78 with a repair loop.

Round 3 (BRIEF-round3.md, e2m/loop/round3.py) ran two experiments on a 30 GPU-hour budget with no calendar deadline, in the order A then B. Part A asks whether preference training is worth keeping once the known collapse risks are removed. Part B asks whether making the model write C first closes the held-out gap. The pipeline started on 17 November 2026 and wrote logs/round3.done at 14:01 Pacific time on 18 November. Terms follow Reports 1 to 3: pass@1 is greedy, pass@5 is the fraction of tasks with at least one passing sample out of five (T = 0.8), the validation set is 90 scaled tasks from the training distribution, and the held-out set is 78 HumanEval and MBPP tasks. A repair loop samples k candidates and repairs for up to R rounds using the visible tests only; scoring uses the full tests.

2Part A: DPO with a supervised term (dpo2) updated 18 Nov 2026

2.1Setup updated 18 Nov 2026

The pairs are the same 46,472 compiler preference pairs as in Report 3 (16,303 default, 15,104 size and 15,065 speed). Three things changed. Goals in the prompt: the assembly prompt already has a goal line (Goal: default|size|speed, from user_asm in e2m/train/format.py), so each pair is now trained with its own goal in that line instead of Goal: default for all of them (pairs_meta.json: choice pair_goal_in_prompt). All pairs were kept. A supervised term: the loss is the DPO preference loss plus 1.0 times the negative log-likelihood of the chosen response, per token (dpo_loss in e2m/train/dpo.py, an RPO-style objective). Gentler settings and a guard: a learning rate ten times smaller, a larger beta, a 1,500-step cap, and a collapse check every 250 steps. The reference log-probabilities come from the model with the policy adapter disabled, as in Report 3.

2.2The collapse guard updated 18 Nov 2026

Before training, lora2 assembles 29 of the 30 guard tasks (0.967). The guard threshold is 80% of that rate, 0.773, so the run would have stopped at any check where 23 or fewer of the 30 assembled. The guard tasks are a fixed subset of the 90 validation tasks (all 30 ids appear in the validation split; a tally of pairs_meta.json against eval.jsonl). Every check passed, and the run kept its final checkpoint (last_good_step 1,500, stop_reason completed).

2.5Reading updated 18 Nov 2026

The supervised term prevents the collapse, but preference training on these pairs does not yet help. With the NLL term, goal-consistent prompts and a learning rate of 5e-6, the model kept producing assembly at every checkpoint, and none of the round 2 failure text appeared. It still ended below lora2 on validation and held-out.

Round 3 changed several things at once (supervised term, goal in the prompt, beta, learning rate, step count), so it does not say which change prevented the collapse. It is consistent with Report 3's first and fifth hypotheses (likelihood displacement and aggressive settings), which these changes target. It does not test the sixth: the pairs still rank two verified programs by size or instruction count, and none was built with a failing program on the rejected side. (The RPO-style objective comes from work where the winner of each pair has a correct answer and the loser a wrong one; Pang et al., 2024.) A preference objective of that kind can teach the model which correct program is smaller or faster; it gives no direct signal toward correctness on unfamiliar tasks, which is where the held-out set is weak. We take this as a reason to park preference training on these pairs, not as evidence that preference training cannot help (§8).

3Part B: C then assembly (c-then-asm) updated 18 Nov 2026

3.1Setup updated 18 Nov 2026

The training set keeps lora2's task mix (sft_lora2.jsonl, 6,781 rows) and changes only the response. Each response is the task's C function followed by the assembly, in one reply with two delimiters, ===C=== and then ===ASM=== (e2m/train/c_then_asm.py, e2m/train/format.py). The C is the task's reference C from the scaled and starter task files. All 6,781 rows found a C source (n_missing_c 0; 3,020 C sources, 2,930 unique task ids). The assembly is the row's existing assembly from the lora2 mix. In a tally of data/scaled/sft_c_then_asm.jsonl, 5,661 rows carry gcc -O2 output and 6 carry gcc -O1 output, and 1,114 rows (source reject_loop) carry a program found by the round 1 rejection-sampling loop, which is not a compilation of the C half shown above it.

The model is a QLoRA on Qwen2.5-Coder-7B-Instruct with the qlora7b-v2 settings (Table 6). At inference the prompt asks for both parts; scoring extracts the assembly half and runs it in the harness as for every other assembly model. Separately, the C half is extracted, compiled with gcc -O2 and run on the same tests (_score_c in e2m/train/eval_generate.py; a compile failure counts as doesnt_assemble, as for the C control). pass@1 and pass@5 for this model refer to the assembly half only.

For he60_sum_to_n ("Return the sum of the integers from 1 through n inclusive"), the reference C uses the closed form n * (n + 1) / 2. The model's C half instead loops from 1 to n, and its assembly half is a plain scalar version of that loop, so it retires 20 times as many instructions on the tests. (The model's own C, compiled by gcc -O2, retires 348 instructions, 66 bytes; the model's hand lowering is slower than gcc's lowering of the same algorithm.) At the other end, for mbpp224_count_set_bits the reference C loops over the bits while the model's assembly uses a single popcntq, giving 0.144. That output passes the tests although it counts only the low 32 bits of the argument (it copies %edi before the popcntq). The other five tasks are at 0.941 to 1.000. The ratio therefore reflects the algorithm the model chose more than the quality of its lowering, and with n = 7 it should not be read as a property of the model.

3.5Reading: where the loss is updated 18 Nov 2026

The fine-tuned model's C is strong, and the loss is in its own lowering to assembly. On held-out, its greedy C passes 48 of 78 tasks, above the C control's 31 greedy. The same replies' assembly passes 7. In 42 tasks the model had a correct program in hand and lost it when it wrote the assembly.

Writing C first did help the model plan: its C is correct far more often than any assembly model's output. It did not make the assembly follow the C. Two observations from this round bear on why, though neither has been tested. The training data never required the assembly to be a lowering of the C above it: the C is the task's reference C, and 1,114 of 6,781 assembly halves are rejection-sampled programs not compiled from that C (§3.1). And the held-out C halves are often not the reference algorithm (instruction ratio 1.877 against the reference, §3.4). The model has seen gcc's lowering of the reference C, not of its own C, so on unfamiliar tasks it is asked to lower a program it has not seen lowered. Since gcc already lowers the model's C correctly whenever the C is correct, the direct route to the held-out gap is to let gcc do the lowering (§8).

4The incomplete held-out loop updated 18 Nov 2026

With budget left after the evaluations, the pipeline ran the held-out repair loop for c-then-asm (loop-c-then-asm-heldout, k = 8, R = 3, T = 0.8, scoring the assembly half). It stopped at its 10-hour stage cap (10.07 GPU hours, exit code 3, "max-hours") after 59 of the 78 tasks. On those 59 tasks it passes 15/59 on the full tests and 21/59 on the visible tests only, with a mean of 24.7 calls per task. The result covers 59 tasks and cannot be stated as a fraction of 78.

7Limitations and caveats updated 18 Nov 2026

  1. Small held-out set. At 78 tasks, differences of two or three tasks (7/78 against 5/78, 9/78 against 12/78) are not differences. No confidence intervals are reported and no run was repeated with another seed.
  2. The C comparison is not matched. The C control is the untrained 1.5B model; the C half comes from a fine-tuned 7B. The step from 31/78 to 48/78 mixes model size, fine-tuning and the C-then-asm prompt. The 7B base model has not been run in C mode.
  3. One configuration per part, several changes at once. dpo2 changed the supervised term, prompt goals, beta, learning rate and step count together, so the cause of the stability is not isolated. c-then-asm is one training run.
  4. Pair accuracy is not comparable across rounds. dpo2's 0.684 is on 256 eval pairs with a loss that includes the supervised term; round 2's 0.902 was on 512 pairs without it.
  5. The collapse guard checks assembly, not correctness, on 30 validation tasks. dpo2 passed the guard while losing correct programs.
  6. Training log. In runs/dpo2/loss.jsonl the logged total loss on a row does not equal the logged preference loss plus the chosen NLL on the same row (for example step 1,500: 0.484 against 0.004 and 0.076). We did not check why (they may come from different micro-batches of the accumulation step). Table 3 therefore reports the two parts, not the total.
  7. The c-then-asm loop is incomplete. It covers 59 of 78 tasks, stopped by its 10-hour cap, and the 19 missing tasks are all from the end of the HumanEval list, not a random subset. Its 15/59 is not a fraction of 78.
  8. Loop budgets are not matched. The C loop uses k = 4, R = 2; the assembly loops use k = 8, R = 3. Loop and single-try results answer different questions (§5).
  9. Ratios over few passes. Size and instruction ratios are means over passing tasks only; the held-out ones cover 2 to 15 tasks, and the 3.584 instruction ratio is dominated by one task (§3.3).
  10. The C-then-asm training data does not tie the assembly to the C. The C is the task's reference C, and 1,114 rows carry assembly that was not compiled from it (§3.1). This is a property of how the set was built, recorded here because it may bear on the lowering result.
  11. C-half scoring depends on the harness. The C half is compiled as a leaf function; an object that references the global offset table is rejected (one held-out case, §3.4).
  12. Tallies computed for this report. The dpo2 log averages (Table 3), the stray-% count, the guard-subset check, Table 8, the any-of-five C counts, the C-half failure categories and ratios, the asm categories for C-only tasks, the source and compiler counts of the training rows, the list of tasks the loop did not reach, and the same-59-task loop comparisons are tallies of eval.jsonl, loss.jsonl, loop.jsonl and sft_c_then_asm.jsonl, not figures in the summaries.
  13. Other. STATUS.md has no round 3 section; the round 3 files are the source. The pytest suite was not re-run for this report, and the human check of a sample of rewritten specifications is still outstanding (Reports 1 to 3).

8Proposed next steps updated 18 Nov 2026

proposed None of the following has been started. Each is a proposal for discussion, and none is a commitment.

  1. Score the model's own C halves as a system (no GPU). The evaluation already compiles each greedy and sampled C half with gcc -O2 and runs it on the tests (§3.4), so no new generation is needed. What is left is to make it a first-class result: a row in the pipeline's results with pass@1, pass@5 and size and instruction ratios from the existing runs/c-then-asm/eval.jsonl, and a check of the C halves that fail for harness reasons (such as the global-offset-table case) rather than wrong logic.
  2. A hybrid route: the model writes C, gcc lowers it, and the model optionally optimizes the result. Take the C half, compile it with gcc -O2, and give the model the gcc assembly to improve for the stated goal, keeping gcc's version whenever the edit fails the tests. The floor is the C-half result (48/78 greedy on held-out); the question is whether the model can then beat gcc on size or speed without losing correctness. Measure on held-out first.
  3. Finish the c-then-asm held-out loop with a larger stage cap or by resuming at task 60, so that it has a 78-task result comparable to the other loops.
  4. Data diversity. Add training tasks closer to the held-out style (short algorithmic functions), checked for overlap with HumanEval and MBPP, and pair each C half with gcc's lowering of that same C, so that the training data teaches lowering of the C actually written. Validation keeps improving while held-out does not, so more of the current mix is unlikely to help.
  5. A matched C control: the 7B base model in C mode, to separate the effect of model size from fine-tuning in Table 10.
  6. Park preference training on the current pairs. Revisit it only with pairs whose rejected side fails (does not assemble or gives a wrong answer), which would test Report 3's sixth hypothesis.
  7. A larger or fresher held-out set with confidence intervals, and repeated seeds for the headline rows.
