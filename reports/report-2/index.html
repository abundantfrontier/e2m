Repair loop and rejection sampling

Technical report 2 of the E2M program: a test-feedback repair loop, one round of rejection sampling, and a second 1.5B LoRA, compared with the Report 1 baselines and the NL-to-C-to-gcc control.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Living paper · Revision 1 · Last updated 14 November 2026 · Companion to the E2M concept paper and technical report 1 · All results are from one 24 GB RTX 3090 workstation · Code and data: github.com/abundantfrontier/e2m

Working paper. You may cite it; see How to cite. Numbers are copied from STATUS.md (section "Repair loop + rejection-sampling round 1") and runs/loop-pipeline/RESULTS.json on the 3090; nothing here is rounded or re-scored. loop-lora2-val was not run.

Abstract

Report 1 ended with a 1.5B LoRA that passed 2 of 78 held-out tasks greedily (pass@1 0.026, pass@5 0.064), a 7B QLoRA at 5 of 78 (0.064, 0.103), and an NL-to-C-to-gcc -O2 control at 0.397 pass@1 and 0.628 pass@5. This report adds a repair loop: sample k candidates, assemble and run them, and feed assemble errors and failures from the visible half of the tests back to the model for up to R rounds, scoring on the full tests. It also adds one round of rejection sampling: full-pass programs from the loop, mixed with gcc-default and rewritten-specification rows, train a second 1.5B LoRA (lora2). On the 78 held-out tasks the loop lifts lora1 from 2/78 greedy to 6/78 (k = 8, R = 3), and lora2 from 4/78 greedy to 10/78. The same loop on the C control reaches 44/78 (k = 4, R = 2). On the scaled validation set lora2 is 38/90 greedy, above lora1 (19/90) and QLoRA 7B (33/90). Held-out assembly is still far from the C control. Visible-only feedback overstates held-out success (lora2: 15/78 on visible tests, 10/78 on all). The pipeline used 46.45 GPU hours against a ~40 h budget and stopped at the budget gate before loop-lora2-val; that run, and DPO, have not been done. All numbers are copied from STATUS.md and runs/loop-pipeline/RESULTS.json on the 3090.

1Goals recap updated 14 Nov 2026

Report 1 (§7) showed that imitating gcc output with a small LoRA does not transfer to held-out tasks: 2/78 greedy for the 1.5B model and 5/78 for the 7B QLoRA, against 31/78 for the same base model writing C that gcc compiles at -O2. Its next steps named the repair loop (best-of-n with test feedback) as the interesting move if the imitation result was far behind the control. This report is that step, plus one round of rejection sampling to see whether the loop's successes make a better training set.

2Repair loop and rejection sampling updated 14 Nov 2026

The package e2m/loop samples k candidates, assembles and runs them in the existing harness (Unicorn by default, QEMU for AVX), then repairs up to R rounds using visible tests only. Scoring uses the full test set. The held-out visible and hidden split is frozen in eval/heldout_visible.json: the first ceil(n/2) tests of each task are visible, giving 199 visible and 153 hidden of 352. Specifications can be rewritten by local Ollama qwen3:14b, with a leakage check against held-out names, n-grams and bge-m3 embeddings. Rejection sampling keeps the programs that pass the full tests, mixes them with the gcc-default SFT rows and rewritten-specification gcc rows, and trains a LoRA of the same 1.5B model (runs/lora2). The stages run through a resumable pipeline, e2m/loop/pipeline.py.

Generated code is still never run on the host CPU.

4lora2 training and greedy results updated 14 Nov 2026

lora2 uses the same recipe as lora1 on Qwen2.5-Coder-1.5B-Instruct: r = 32, alpha = 64, dropout 0.05, learning rate 2e-4, 3 epochs, batch 2 × accumulation 8, bf16. runs/lora2/summary.json records 6,713 train examples (68 dropped over the p99 length of 1,343 tokens, max length 1,344), 1,260 steps, a final train loss of 0.152 and 3,226 s of training. The in-training validation set was empty (val_tasks=0) because the mix had already dropped the validation and held-out task ids.

pass@1 is greedy. pass@5 is the unbiased estimator on 5 samples at T = 0.8; with n = 5 that equals the fraction of tasks with at least one correct sample.

Against Report 1, lora2 on held-out is 4/78 greedy (0.051) and 5/78 at pass@5 (0.064): above lora1 (2/78, 0.026) on pass@1, the same on pass@5, and just under QLoRA 7B (5/78, 0.064; pass@5 0.103). Validation tasks come from the same distribution as training, so this is not evidence of transfer; the held-out set is the transfer test.

6GPU hours updated 14 Nov 2026

The pipeline stopped at the GPU-hour gate. e2m.loop.pipeline.remaining_ok returns false once gpu_hours_used() >= 40.0, and the pipeline then exits with code 3. After loop-lora2-heldout finished with code 0, used hours were 46.45 (167,225.43 s). loop-lora2-val (about 1.5 h) did not start. The rewrite and training rows are from the same file as Table 7.

lora1 loop held-out pass, mbpp8_square_nums, at call 31: an AT&T loop that squares (%rdi,%rax,8) into (%r8). The C repair loop passes the same mbpp3_is_not_prime task at call 4 with a C trial-division function compiled by gcc -O2.

A visible-pass, full-fail case: lora2 loop on mbpp45_array_gcd passes the visible tests at call 2; later attempts use shrq %r8d (a q suffix on a 32-bit register) and doesnt_assemble.

8Limitations and caveats updated 14 Nov 2026

  1. loop-lora2-val was not run. The validation loop column therefore has lora1 only.
  2. Budget overrun. The pipeline used 46.45 GPU hours against a ~40 h budget; it stopped at the gate, not at a stage failure.
  3. Partial rejection coverage. The rejection loops covered 1,800 of 2,910 original train tasks and 1,301 rewritten tasks.
  4. No in-training eval loss for lora2 (val_tasks=0).
  5. Stage 4 not started. DPO on data/scaled/pairs.jsonl, the 7B recipe, and a 7B base-assembly baseline have not been run.
  6. Small held-out set. At 78 tasks, 4/78 versus 5/78 is not a meaningful difference, and neither are single-digit loop gaps without repeated runs. No confidence intervals are reported.
  7. Different loop budgets. The C loop uses k = 4, R = 2; the assembly loops use k = 8, R = 3. They are not matched.
  8. Tests. pytest tests/test_loop.py tests/test_eval_summary.py: 13 passed. The full suite was not re-run for this report.
  9. Specifications. The human check of a sample of specifications is still outstanding (Report 1, §9).

9Next steps updated 14 Nov 2026

  1. Run loop-lora2-val when GPU time is available, so the validation loop column matches lora1.
  2. A second rejection-sampling round with lora2, or DPO on the 46,472 preference pairs gated on held-out correctness.
  3. Close the gap to the control. Held-out is lora2 loop 10/78 against C loop 44/78 and C greedy 31/78.
  4. Human check of a sample of rewritten specifications before drawing conclusions from rewritten-spec rows.
