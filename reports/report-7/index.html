The C path's ceiling: a matched repair loop, and an untrained 7B that writes better C than the fine-tuned one

Technical report 7 of the E2M program. It covers round 6, the first round since round 1 with no training. Round 6 measured the ceiling of the practical system, "the model writes C and gcc lowers it", with a repair loop matched to the assembly loops. It also ran the untrained 7B in C mode, a control Report 5 left open, and re-scored existing results by function size and against gcc -Os.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Abstract

Report 6 closed the direct-assembly line of work. Across seven recipes the model's own assembly passes 4 to 7 of the 78 held-out tasks, while letting gcc lower the model's C passes 46 to 48. Round 6 ran on a 5 GPU-hour budget and used 2.00 hours. It asked how far the C path goes.

  1. The C repair loop clears the bar set before the run.
    • Setup: c-only-7b writes C, gcc -O2 compiles it, and the visible tests give feedback (k = 8, R = 3, the same settings as the assembly loops).
    • Held-out: 64/78 pass the full tests (69/78 pass the visible tests), with a mean of 8.2 model calls per task. Validation: 76/90.
    • That is above the 55/78 decision threshold stated before the run, 16 tasks above the best single-try hybrid (48/78), and more than three times the best assembly loop (19/78).
  2. The untrained Qwen2.5-Coder-7B-Instruct writes better C than our fine-tuned C model.
    • Greedy with no loop, it passes 63/78 held-out (66/78 at pass@5), against 46/78 for c-only-7b under the same eval protocol. On validation the two are level (61/90 against 62/90).
    • On held-out the base model passes 19 tasks the fine-tuned model fails, and the fine-tuned model passes 2 the base fails.
    • We checked the protocol: same weights directory, same 4-bit loading, same prompt and token limit, and the stored c-only-7b outputs re-score to exactly 46/78 with today's harness. The gap is real.
    • Fine-tuning on our training mix cost the C model about 17 held-out tasks. It also means Report 5's step from the 1.5B C control (31/78) to about 47/78 came from model size, not from fine-tuning.
  3. With a loop and the base model together, 70 of 78 held-out tasks have a correct C program.
    • Of the 14 loop failures, 5 pass the visible tests but fail hidden ones, 7 end in wrong answers, 1 crashes, and 1 is blocked by the harness rule against GOT references.
    • The untrained 7B's greedy C passes 6 of the 14.
  4. gcc is a strong bar on code quality.
    • On the 64 loop passes, the code is the same size as gcc -O2 on the reference C at the median (mean 1.052) and has the same instruction count at the median (mean 1.595, driven by one task at 34×).
    • Against gcc -Os on the reference, the passing code is 1.51× larger at the median, and only 7 of 64 programs are smaller.
    • So the open problem is code quality: beating the compiler on programs that are already correct.

The next step is a round that tries to beat gcc -O2 and -Os, and clang, on size and speed for the programs that already pass, with no further correctness training (§9).

1Goals recap updated 26 Nov 2026

Report 6 (§10) proposed measuring the ceiling of the C path, closing the model-size versus fine-tuning confound, and fixing the validation signal. Round 6 (BRIEF-round6.md, approved 26 November 2026, 7:48 AM PT) did this in four GPU stages plus a CPU summary. It used no training and no courtesy time gate, and had a 5.0 GPU-hour hard cap.

The decision rule was set before the run:

  • A C loop result of 55/78 or more makes the C path the system, and the next round works on beating gcc's output.
  • A result below 50/78 makes C quality the bottleneck.

The pipeline held the GPU lock from 7:53 to 9:53 AM PT on 26 November, and every stage finished OK.

Terms follow Reports 1 to 6:

  • pass@1 is greedy, and pass@5 is at least one pass in five samples at T = 0.8.
  • The held-out set is 78 HumanEval and MBPP tasks. Validation is 90 ExeBench tasks.
  • Loop scores are "passed all tests" out of n, with feedback from the visible tests only.
  • Size and instruction ratios are means over passes against gcc -O2 on the task's reference C, unless stated otherwise.

2Method updated 26 Nov 2026

2.1C repair loop updated 26 Nov 2026

The loop used the existing e2m.loop run --mode c with the c-only-7b adapter (round 4) on 4-bit Qwen2.5-Coder-7B-Instruct, with k = 8, R = 3 and T = 0.8. Each candidate C is compiled by gcc -O2 and run on the visible tests. Failures are fed back, and the final program is scored on the full tests.

The held-out tasks were run in an order that interleaves MBPP and HumanEval (runs/round6/heldout_order.json), so a run stopped at its cap would still cover both. Neither loop hit its cap: held-out took 0.90 h and validation 0.86 h.

2.2Untrained 7B in C mode updated 26 Nov 2026

The base model was the same weights directory as every 7B adapter (runs/models/Qwen2.5-Coder-7B-Instruct, the Hugging Face Qwen2.5-Coder-7B-Instruct, with no E2M adapter). It was loaded in 4 bits, prompted with the same C prompt through eval_generate --mode c, and scored greedy plus five samples, on held-out and validation.

The round 4 c-only-7b evaluation used the same script, mode, 4-bit loading and token limit (1,536 new tokens). The only difference is the adapter.

2.3CPU re-scores updated 26 Nov 2026

The CPU work had two parts:

  • Existing greedy results were bucketed by the size of gcc -O2 on the reference C: small (40 bytes or less) or large.
  • The reference C of every held-out and validation task was compiled with gcc -Os as well as -O2. This makes the size comparison with the model like for like, an open caveat in Report 5, §8.

Is the comparison fair? We checked four things:

  1. The base model is the Instruct checkpoint that every 7B adapter was trained on (its README identifies it as Qwen2.5-Coder-7B-Instruct).
  2. The eval command for c-only-7b in round 4 (logs/build-round4.log) differs from round 6's only in --adapter.
  3. Re-scoring the 78 stored c-only-7b greedy held-out programs with the current harness reproduces 46/78 exactly (78/78 agreement), so the harness has not drifted.
  4. No stored output was truncated: the longest is 788 characters, against a stored limit of 1,500.

What fine-tuning changed.

  • On the 19 tasks where only the base model passes, the fine-tuned model's C fails by wrong answer in 14, does not compile in 3, and crashes or times out once each.
  • The fine-tuned model writes shorter code (median 167.5 characters against 236.5) and, like its training targets, never uses a code fence. In the examples we read by hand, it takes shortcuts the specification does not support:
    • In mbpp78_odd_setbit_count it returns a popcount-parity formula, where the base model counts in a loop.
    • In mbpp76_count_squares it counts square positions along one dimension only, where the base model computes the sum over both dimensions.
    • In mbpp32_max_prime_factor its trial-division bound is off by one.
  • On validation, which has the same ExeBench style as the training data, the two models are level.

Reading. The training data for c-only-7b was the 6,781-task mix: rewritten specifications of mostly very small ExeBench functions, with their terse reference C as the whole response. Fine-tuning on it narrowed the model toward that style, which is neutral in distribution and costly on unfamiliar HumanEval and MBPP prose.

This is the likely explanation, not a tested one. We have not varied the learning rate, epochs or mix (§8).

It also corrects Report 5, §2.3. There, the step from the untrained 1.5B C control (31/78) to about 47/78 was attributed to "the fine-tuned 7B". The untrained 7B alone gives 63/78, so the step is model size, and our fine-tuning removed part of it.

Three patterns:

  • Visible-test overfitting (5). The loop's feedback can only see half of each task's tests. Five tasks end with a program that passes those and fails at least one hidden test.
  • Persistent misreadings (7 wrong answers, 1 crash). Three of these are bit-manipulation specifications (mbpp48, mbpp155, mbpp24) that neither model reads correctly.
  • Harness limitation (1). he16 needs a lookup table, and the harness rejects any object that references the global offset table. This is a constraint of the evaluation, not a model failure.

The untrained 7B's greedy C passes 6 of the 14, so the two together cover 70/78 (71/78 counting its pass@5 samples). The loop has not been run on the untrained model; Table 5 suggests it would be stronger than the fine-tuned loop.

Across all 78 held-out tasks, gcc -Os on the reference C is 0.671 of -O2's size on average, and 0.863 on validation.

Report 5's -Os hybrid ratio (0.691) compared the model's C at -Os with the reference at -O2. Compared at the same flag, the hybrid's passing code is 0.999 (c-only-7b) and 0.975 (c-then-asm) of the reference at -Os. Most of the earlier saving was the flag.

The instruction mean is dominated by algorithm choices in a few tasks:

  • he75_is_multiply_prime runs 34× the reference's instructions, as in Report 5.
  • Four other tasks run 1.85× to 3.23× the reference (he77_iscube, mbpp76_count_squares, he139_special_factorial, he114_min_subarray_sum).

Reading. On correctness, the C path is close to saturating this held-out set. On code quality, it matches gcc at the median, because it is gcc. Beating a compiler at -O2 or -Os is the remaining research question, and it now has a correct starting point on 64 to 70 of 78 tasks.

8Limitations and caveats updated 26 Nov 2026

  • Small set, one seed. At 78 tasks, 63 against 64 is not a difference, and the base-against-fine-tuned gap (17 tasks) is one run of each, with no confidence interval.
  • Fine-tuning was not ablated. The explanation in §3.2, a narrow and terse training target, has not been tested. A lower learning rate, fewer epochs, a mix with held-out-like prose, or keeping the base model's code-fence and comment style could each change the result.
  • The loop used the fine-tuned model. We did not run the loop on the untrained 7B, which on this evidence would probably do at least as well.
  • Visible-test overfitting. Five loop failures pass the visible tests only. Any loop or search that accepts programs on the visible tests needs a second check, such as differential testing against a reference on generated inputs.
  • Harness constraints. Leaf functions only, with no GOT references. A pass means the tests pass in the emulator, not that the program is correct (Report 5, §3.3).
  • Ratios. Ratios are against gcc on the reference C, not against the best available compiler. clang and -O3 were not measured.
  • Copied numbers. Round 4 rows are copied, not re-scored, except the c-only-7b re-score check in §3.2.

9Proposed next steps updated 26 Nov 2026

proposed None of the following has been started; each is for discussion.

  1. Beat the compiler on correct programs (round 7). Start from the programs that already pass. Build a compiler-portfolio baseline per task: gcc -O2, -O3 and -Os, and clang -O2 and -Oz. Then let the model propose smaller or faster assembly, or faster C, for a stated goal. Accept a variant only if it passes the full tests and agrees with the compiled C on generated inputs. Success means strictly beating the best compiler on a meaningful number of tasks with zero accepted regressions.
  2. Use the untrained 7B as the C writer, and run its loop. The base model is the better C writer. A base-model C loop (about 1 GPU hour) is a cheap check of the 70/78 union.
  3. No more correctness fine-tuning on the current mix. If C fine-tuning is revisited, it should be a small ablation (learning rate, epochs, prose specifications, keeping the base model's style) measured on held-out, not on validation.
  4. Differential testing everywhere. Use it to catch visible-test overfitting in loops, and as the acceptance check for any optimized variant.
  5. Harder validation split. As in Report 6, §10: tasks that are not from ExeBench and functions larger than about 40 bytes.
