Beating the compiler on code that already works: blind search does most of it, and our checker needed a second look

Technical report 8 of the E2M program. It covers round 7, the second round in a row with no training. Round 7 took the programs that already pass and asked whether the untrained 7B, a blind search, or both could beat the best of five compiler settings on code size or on executed instructions without breaking them.

Boyd Wilson, Abundant Frontier Institute and Omnibond Systems

Abstract

Report 7 found a correct C program for 70 of 78 held-out tasks, but that code was gcc -O2-sized at the median and 1.51× larger than gcc -Os. Round 7 asked whether anything we have can beat the compiler on programs that already pass. It ran on a 4 GPU-hour budget and used 2.55 hours.

  1. The bar is the best of five compiler settings, not gcc -O2.
    • Every pass-set program and the reference C were compiled with gcc -O2, -O3 and -Os, and with clang -O2 and -Oz.
    • On held-out, the best-size compile is 0.544× gcc -O2 at the median and 0.957× gcc -Os. clang -Oz sets the size bar on 34 of 73 tasks and gcc -Os on 28.
    • A model-written C program, not the reference, sets the size bar on 18 of the 73.
  2. A blind search beat that bar much more often than the model did.
    • After our audit, held-out has 27 tasks with strictly smaller verified code and 3 tasks at ≤ 0.9× the instructions, out of 73.
    • Of the 27 size wins, search found 25 and the model 3 (one task is shared). Of the 3 speed wins, search found 2 and the model 2 (one task is shared).
    • The wins are small: the median winning size is 0.923× the bar, and the mean over all 73 tasks is 0.967×.
  3. The model's unique contribution is real but tiny.
    • On held-out, three wins come only from the model:
      • mulq for a 2-byte-shorter cube.
      • A freed register in a digit loop.
      • popcnt replacing a bit-counting loop (104 → 24 instructions).
    • On held-out, the model attempted all 73 tasks for both goals within 2.51 GPU hours. On validation it reached only 8 tasks before the cap. Search ran on all 150 tasks.
  4. Our first checker was too weak, and the decision is Partial.
    • Three accepted search variants failed the planned 5,000-input re-check. All three truncated 64-bit values to 32 bits.
    • A post-run audit used wider input families. It found 16 more of the 61 surviving wins were wrong.
    • Some of these were constant outputs. Others ignored the length argument or failed on equal inputs, and two were model wins.
    • Under the rule fixed before the run (zero re-check failures), round 7 is Partial. The audited counts still clear the 10-task bar for size, and the model does beat search on some goal.
  5. Faster C did not help. Eight held-out tasks run more than 1.5× the reference's instructions. Asking the model for a faster algorithm produced no verified win over the best compiler.

The next step (§9) is CPU-first. It builds a coverage-guided equivalence checker that the round-7 failures cannot pass, re-validates every round-7 win with it, and scales the search. It also gives the model at most 1 GPU hour, and only on tasks where search gets close but does not win.

1Goals recap updated 26 Nov 2026

E2M's goal is machine code from English that is better than what a compiler produces. Report 7 showed that correctness is mostly solved by the C path: model C lowered by gcc passes 64/78 held-out with a repair loop and 63/78 greedy with the untrained 7B. What remains is quality.

Round 7 set the bar at the best of five compiler settings on the best available C for each task. It then measured two ways to go past that bar on the same starting code: model-proposed assembly edits and a blind stochastic search.

The decision rule was fixed before the run:

OutcomeRule
Win≥ 10 held-out tasks strictly smaller than best_size, or ≥ 10 at ≤ 0.9× best_speed; the model beats search on at least one goal; zero accepted variants fail hidden tests or a 5,000-input re-check.
PartialWins only from search, or fewer than 10.
No winNo strict wins on either goal.

2Method updated 26 Nov 2026

2.1Pass set and oracle updated 26 Nov 2026

  • Pass set. A task is in the pass set when it has at least one passing C program from these sources, kept in this order:
    1. The round 6 C loop's best pass.
    2. The untrained 7B's greedy C, plus its passing samples.
    3. The round 4 hybrid's C.

    Up to six distinct programs are kept per task. The first one is "the pass-set C" used in prompts. The pass set covers 73 held-out and 77 validation tasks.

  • Oracle. gcc -O2 of the task's reference C. This is stricter than the proposal, which used gcc -O2 of the passing C.
  • Acceptance. A variant is accepted when it passes every test (visible and hidden) and agrees with the oracle on 500 generated inputs (e2m/harness/diff.py).
    • The inputs are type-preserving mutations of the task's tests. Ints are drawn over edge values, ranges, wide 33- to 62-bit values and k·2³²+small. Buffer lengths are kept. Strings are redrawn from the tests' alphabet with varied lengths.
    • The candidate runs from an adversarial entry state that the ABI allows: random flags, random rax, r10, r11 and unused argument registers, and random bits 32–63 above narrow int arguments. This is a new opt-in entry_noise option in the emulator.
  • Checker self-test. Before the run, the checker agreed on 10 of 10 equivalent pairs and caught 10 of 10 known-different pairs. The different pairs were round 6 programs that passed visible tests but failed hidden ones; the checker was seeded from visible tests only. It also handled 3 of 3 hand-kept adversarial cases correctly: 32-bit truncation, reliance on entry flags, and a control.
  • Metrics. Size is bytes of .text. Speed is emulator instructions executed, summed over the task's tests.
  • Win thresholds. A size win is strictly below best_size. A speed win is at most 0.9× best_speed. Every claimed win is re-checked on 5,000 fresh inputs.

The model and search started from the same listing and used the same acceptance check. Their budgets were different: search had 16 CPU-hours (850,672 candidates), and the model had 2.5 GPU-hours (about 3,800 candidates). §8 covers this.

Three findings:

  • The size bar is roughly half of gcc -O2 on held-out.
  • clang -Oz is the best size setting most often. It uses tricks such as push $imm; pop %reg.
  • On speed, gcc -O2 is already the best setting at the median.

On a quarter of the tasks, the bar comes from a model-written C program compiled by the best setting, not from the reference C. Before this round, "beat gcc -O2" was the bar in our tables. This bar is much harder.

4.3What search found updated 26 Nov 2026

  • Search's 25 held-out size wins are mostly 1–5 byte savings, such as removing a redundant mov, shortening operands to 32 bits where the value provably fits, and dropping a bounds check that can never fire.
  • One large win is he77_iscube, 64 → 52 B. Search removed a loop guard (r + 1 <= 2642245) that cannot bind for any int64 input. We checked that by hand.
  • he24_largest_divisor, 49 → 31 B, is listed as questionable. It drops the d*d <= n bound and tests the remainder with a 32-bit testl. It returns the same results on every input the emulator can reach, but it is correct only while divisors stay below 2³², and it is asymptotically slower.
  • The 45 wins that survived the audit were also stress-tested with ints drawn mostly from the wide (31- to 62-bit) range. All passed, except one whose reference cannot run on such inputs.

5Re-check failures and the post-run audit updated 26 Nov 2026

5.1The planned 5,000-input re-check updated 26 Nov 2026

The summary re-checked all 64 claimed wins (57 search, 7 model) on 5,000 fresh inputs. Three failed, all search size wins, and all for the same reason: a movq → movl rewrite that truncates a 64-bit value.

he131_odd_digit_product65 → 61 B32-bit copies of a 64-bit product1,183

None of them failed the hidden tests. All three passed the full test suite, and all accepted variants pass hidden tests by construction. These failures alone make the outcome Partial under the fixed rule.

5.2The post-run audit updated 26 Nov 2026

The cheats that slipped through suggested a whole class of blind spots, not three bad draws. So we re-checked all 61 surviving wins on 5,000 inputs from wider families. These are families="v2" in diff.py, written after looking at the round-7 wins:

  • Log-uniform float magnitudes.
  • Newline, tab and the full printable set in strings.
  • Equal and shared-prefix string pairs.
  • Equal numeric buffers and scalars.
  • Buffers resized from 0 to 700 elements together with their length argument.
  • Tiny ints.

16 of the 61 are wrong.

Kind of blind spotWins removedExample
Constant output the generator never challenged6delta_AT returns 10.0 always (inputs never reach the leap-second dates); checkmd5 always returns −1 (random strings are never equal); az_paragraph_num_lines always returns 1 (no newline in the tests' alphabet)
Length argument kept equal to the buffer length6ehstrnlen ignores the NUL; he85, he100, he120 and he152 fail or crash at n = 0 or small n
Equal inputs never generated2CmpDoubles (model) returns −1 for equal values; ehnlc_strncmp loops when max_len = 0 and the strings are equal
Long arrays never generated1he3_below_zero (model) writes only %al, so it is wrong once the index passes 255
Other edge input1he114 size: returns a sum for n = 0 with a non-empty buffer

The v2 families produce no false positives on the 10 equivalent self-test pairs at 2,000 inputs each.

The lesson is that the checker was blind to these mistakes, and search exploits exactly what a checker cannot see. Search accepted 40 wins that survived and 16 that did not, and it generated 850,672 candidates against our input distribution. Most of the 301,512 candidates that passed all tests were never shown to the checker, because they were not improvements.

5.3Decision updated 26 Nov 2026

The decision is Partial. Three accepted variants failed the pre-registered 5,000-input re-check, and the audit removed 16 more.

Taken by themselves, the audited numbers would meet the other two conditions:

  • 27 held-out size wins against a bar of 10.
  • 3 held-out tasks where only the model wins.

But the rule was zero failures, and the checker that produced the wins is the thing that failed.

6Faster C for algorithm-bound tasks updated 26 Nov 2026

Eight held-out tasks have a pass-set C that runs more than 1.5× the reference's instructions under gcc -O2. They range from he75 at 34× to he120 at 1.52×. For each, the model was asked for a faster algorithm (k = 8), which was compiled with gcc -O2/-O3 and clang -O2.

  • None beat the best compiler by 10%.
  • he114_min_subarray_sum went from 1.535× to 0.599× of gcc -O2 on the reference, 121 instructions against a bar of 133 (0.91×). That is close, but not a win.
  • On six of the eight tasks, no faster program passed acceptance.

The stage took 0.04 GPU hours.

8Limitations and caveats updated 26 Nov 2026

  • Unequal budgets. Search had about 16 CPU-hours and 850k candidates. The model had 2.5 GPU-hours and about 3,800 candidates, and on validation it covered only 8 tasks. The comparison is "what each got for this run's budget", not a matched-compute comparison.
  • The audit is post hoc. The v2 families were written after we looked at the wins. The audited counts are therefore an upper bound on wins that a checker designed in advance would accept. They may still contain wrong programs that neither family set exercises.
  • The bars were not audited. About a quarter of the bars come from model-written C. If one of those programs is subtly wrong and smaller than a correct compile, the bar is too strict. That makes the win counts conservative, not inflated.
  • Speed is counted instructions, not cycles. popcnt counts as one instruction and needs POPCNT hardware; a removed mov counts the same as a removed div. A cycle model such as llvm-mca, or real timing, could reorder the speed results.
  • Small functions. Held-out functions are 10–300 bytes. A 1–5 byte saving is a real percentage, but nobody would ship it.
  • One model, untrained, no examples. The model got no worked examples of size or speed tricks, no tool use, and refinement feedback of at most two rounds.

9Proposed next steps updated 26 Nov 2026

The results point at the checker first and the model last.

  1. Make accepted wins stay accepted (CPU). Build a checker that the round-7 failures cannot pass:
    • Coverage-guided inputs. Mutate until the generated inputs reach every basic block of the oracle and both sides of every branch.
    • The v2 families, plus a "held-back" family set written by someone other than the person tuning the search.
    • Rejection of any candidate whose outputs vary less than the oracle's across the input set.
    • Re-validate all round-7 wins and report them.
  2. Scale search (CPU).
    • Run it with 16 workers for 6 hours under the new checker, starting from all five compiler listings, not only the best.
    • Add the model's winning ideas as moves: one-operand mul, popcnt/lzcnt/tzcnt behind a flag, register reuse, and push/pop constants.
  3. Use the model only where search stalls (GPU, ≤ 1 h). Ask for k = 8 proposals only on tasks where search is within a few bytes or 10% of a win. Keep this stage only if it adds at least 3 unique verified wins per GPU hour.
