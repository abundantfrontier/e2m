Let gcc do the lowering: a matched C control, a gcc hybrid, and where the model's assembly goes wrong

Technical report 5 of the E2M program: a 7B QLoRA trained to write C only, matched to the C-then-assembly model; a hybrid in which the model writes C and gcc lowers it; the completed C-then-assembly held-out repair loop; and a classification of the held-out tasks where the model's C passes and its own assembly fails.

Abstract

Report 4 found that a 7B model trained to write C and then assembly writes correct C for 48 of the 78 held-out tasks but correct assembly for only 7, and that the comparison with the C control mixed model size with fine-tuning. Round 4 ran four parts on a 30 GPU-hour budget and used 7.81 hours. Part A trained the same 7B base on the same tasks with C as the only target. Compiled by gcc -O2, its C passes 46/78 greedy and 56/78 at pass@5 on held-out (62/90 and 72/90 on validation), close to the C-then-asm model's C half (48/78 and 61/78; 63/90 and 70/90). Training on the assembly target therefore neither helps nor hurts the C, and the step up from the untrained 1.5B C control (31/78) comes from the fine-tuned 7B, not from the assembly half. Part B scored the hybrid "the model writes C, gcc lowers it" against the model's own assembly: on held-out, 48/78 against 7/78 greedy for the C-then-asm model. Compiling the same C with -Os passes exactly the same tasks at 0.691 of the reference's -O2 size. The hybrid's mean instruction ratio of about 1.9 is driven by a few tasks where the model chose a slower algorithm than the reference; the median is 1.000. Part C finished the C-then-asm held-out repair loop: 19/78 on the full tests and 27/78 on the visible tests, above the qlora7b-v2 (12/78) and lora2 (10/78) loops and far below the 1.5B C loop (44/78). Part D classified the 42 held-out tasks whose C passes and whose assembly fails: 23 wrong answers, 9 crashes, 9 timeouts, 1 that does not assemble and none flagged for the calling convention. The model's assembly almost always assembles and looks like gcc output, but in most of these tasks it does not compute what its own C computes. The practical system today is the hybrid; the research question becomes how to get from it to assembly that beats gcc without losing correctness.

1Goals recap updated 21 Nov 2026

Report 4 left three open items. First, the C-then-asm 7B (c-then-asm) writes C that passes 48 of 78 held-out tasks when gcc -O2 compiles it, against 31/78 for the C control, but the C control is the untrained 1.5B model, so model size, fine-tuning and the assembly target were mixed together. Second, the same model's own assembly passes 7 of those 78, so most of what it gets right is lost in its own lowering. Third, its held-out repair loop stopped at the 10-hour stage cap after 59 of 78 tasks.

Round 4 (BRIEF-round4.md, approved 20 November 2026) addressed these in four parts, run in the order A, B, C, D: a matched 7B C control (A), a hybrid that lets gcc lower the model's C (B), the rest of the held-out loop (C), and a classification of the C-pass, assembly-fail tasks (D). The budget was 30 GPU hours with a 10-hour cap per stage and no calendar deadline. The pipeline wrote logs/round4.done at 04:33 Pacific time on 21 November with every stage ok. Terms follow Reports 1 to 4: pass@1 is greedy, pass@5 is the fraction of tasks with at least one passing sample out of five (T = 0.8), the validation set is 90 scaled tasks from the training distribution, and the held-out set is 78 HumanEval and MBPP tasks. Size and instruction ratios are means over greedy passes against gcc -O2 on the task's reference C, and instruction counts are emulator retire counts.

2.3Reading updated 21 Nov 2026

Training on the assembly target neither helps nor hurts the model's C. A 7B trained on C alone writes C about as well as the 7B trained on C followed by assembly (46/78 against 48/78 greedy on held-out). The step up from the untrained 1.5B C control (31/78) is therefore a property of the fine-tuned 7B, not of the assembly half of the C-then-asm response.

This settles the question Report 4 left about the assembly target, but not the whole confound. Both 7B models are fine-tuned, and the C control is an untrained 1.5B, so the step from 31/78 to about 47/78 still combines model size and fine-tuning on these tasks. Separating those two would take the untrained 7B in C mode or a fine-tuned 1.5B in C mode (§9). For the system question that follows, the relevant fact is that the fine-tuned 7B writes C that passes about 60% of held-out tasks greedy, with or without the assembly target.

3Part B: the gcc hybrid updated 21 Nov 2026

3.1Setup updated 21 Nov 2026

The hybrid is "the model writes C, gcc lowers it". For both 7B models, the pipeline took each greedy and sampled C output (for c-then-asm, the C halves already in runs/c-then-asm/eval.jsonl; for c-only-7b, its own evaluation), compiled it with gcc -O2 and with gcc -Os, and scored the resulting code in the same harness as every assembly output. No new generation was needed for this stage, which took 163.89 seconds of CPU time. c-only-7b has no direct assembly to compare against; the direct-assembly row is the c-then-asm assembly half.

On held-out, letting gcc lower the C-then-asm model's C passes 48 of 78 tasks greedy against 7 for the same model's own assembly, and 61 against 9 at pass@5. On validation the gap is smaller (63 against 40 greedy, 70 against 54 at pass@5), in line with the validation and held-out gap reported since Report 3. The -O2 hybrid rows reproduce the C-half figures copied from round 3 (63/90 and 48/78), which is expected: they compile the same C with the same flags.

-Os. Compiling the same C with -Os passes exactly the same tasks as -O2, greedy and at pass@5, for both models and both sets (a tally of hybrid.jsonl). On held-out the passing code is 0.691 (c-then-asm) and 0.670 (c-only-7b) of the size of gcc -O2 on the reference C, at an instruction ratio of 2.019 and 2.028. The size saving comes mostly from the flag, not from the model: the reference is compiled at -O2, and gcc -Os on the reference C was not measured, so Table 3 does not say how the model's C compares with the reference at the same optimization level.

One task, he75_is_multiply_prime, accounts for most of the excess for both models. The specification asks whether the input is the product of three primes, each at most 100. The reference C divides out prime factors and counts them. Both models instead write three nested loops over candidate factors up to about 100 and test whether their product equals the input, which retires about 30 times as many instructions on the tests. (Neither loop checks that the factors are prime, so both would accept 16 = 2 · 2 · 4, which the specification rejects; the held-out tests do not catch this.) The second task is he60_sum_to_n, the case behind Report 4's 3.584: both models loop from 1 to n where the reference uses the closed form. Without these two tasks the mean is 1.094 and 0.970, and the median pass retires the same number of instructions as the reference. The ratio of about 1.9 therefore reflects a few algorithm choices, not a general cost of letting gcc lower the model's C.

3.4Reading updated 21 Nov 2026

The model writes C, and gcc lowers it, is the practical system today. On held-out it passes 48 of 78 tasks greedy and 61 at pass@5, against 7 and 9 for the same model's own assembly. On most passing tasks its code is as fast as gcc on the reference C, and -Os trades instruction count for size without losing a single pass.

The hybrid does not by itself meet the program's goal of machine code that is better than a compiler's: it is a compiler's output by construction. What it provides is a correct starting point on about 60% of unfamiliar tasks, from which a model could try to improve size or speed while keeping the tests passing (§9). Where its code is slow, the cause in Table 4 is the algorithm in the C, which is a matter for the C-writing step, not for the lowering.

Of the 19 new tasks, 4 passed on the full tests (he102_choose_num, he122_add_elements, he138_sum_of_four_evens, he159_eat) and 6 on the visible tests (a tally of loop.jsonl; the first 59 still give 15 and 21, as in Report 4).

5Part D: why the assembly fails where the C passes updated 21 Nov 2026

On held-out, the greedy outputs of c-then-asm split into 6 tasks where both halves pass, 42 where only the C passes, 1 where only the assembly passes and 29 where neither does (agreement 35/78). Part D classified the 42 C-pass, assembly-fail tasks using the harness labels already stored on the assembly half (runs/round4/failure_analysis.md, failure_tally.json).

These counts match the Report 4 tally of the same file (23, 9, 9 and 1). In 41 of the 42 tasks the assembly assembles, and the harness flags none for the calling convention. The assembly reads like gcc output, down to the .p2align padding directives, and uses the right argument registers. In more than half of the tasks it then runs to completion and returns the wrong value, and in the other 18 it crashes or does not finish within the limit. The crashes in the examples are reported as accesses to unmapped memory.

Two short examples from failure_analysis.md and runs/c-then-asm/eval.jsonl show the pattern. In he102_choose_num (logic mismatch: "return 4294967295 != expected 14") the C half is a correct six-line function. The assembly copies y into %rax and then tests its low bit with andl $1, %eax, which overwrites the copy, so the following subq $1, %rax subtracts from the bit rather than from y; and the −1 path writes movl $-1, %eax, which returns 4,294,967,295 rather than −1 as a 64-bit value.

int64_t he_choose_num(int64_t x, int64_t y) {     he_choose_num:
  if (x > y) return -1;                             movq  %rsi, %rax
  if ((y & 1)) {                                    cmpq  %rdi, %rsi
    if (y - 1 < x) return -1;                       jl    .L2
    else return y - 1;                              andl  $1, %eax
  } else { ... }                                    je    .L3
                                                    subq  $1, %rax
                                                    ...
                                                .L2: movl  $-1, %eax
                                                    ret

In he25_factorize (timeout) the C half is a correct trial-division loop that writes each factor to an output array. The assembly half has the shape of a gcc loop but none of its content: it multiplies by a register that has not been set (imulq %rcx, %rdx), contains no division and never stores to the output array, and runs until the harness stops it (2,216,493 instructions, against 238 for gcc's lowering of the model's own C).

The model's assembly usually assembles and follows the calling convention, but it does not implement its own C. The loss is semantic, not syntactic: register reuse, operand width and missing loop bodies, in code that otherwise looks like compiler output.

This is consistent with the observation in Report 4 that the training data never required the assembly half to be a lowering of the C half above it (§3.5 there): the model has learned what gcc output looks like, but has not learned to lower the particular program it just wrote. We have not tested that explanation; §9 proposes training data and a check that would.

8Limitations and caveats updated 21 Nov 2026

  1. Small held-out set, one seed. At 78 tasks, differences of a few tasks (46 against 48, 56 against 61) are not differences. Every model here is one training run with one seed, and no confidence intervals are reported.
  2. The size and fine-tuning confound is narrowed, not removed. c-only-7b shows that the assembly target does not account for the gap to the C control, but both 7B models are fine-tuned and the C control is an untrained 1.5B. The untrained 7B and a fine-tuned 1.5B have not been run in C mode.
  3. Copied prior numbers. Rows for lora2, qlora7b-v2, c-then-asm (asm half, C half and agreement) and the 1.5B C control were copied by the round 4 pipeline from runs/round3/RESULTS.json, not re-scored. The hybrid -O2 rows recompile the stored C halves and agree with the copied C-half figures.
  4. The harness. Every result runs single functions in the Unicorn emulator (QEMU for AVX) on the task's tests. A pass means the tests pass, not that the program is correct: he75_is_multiply_prime passes for both models with a predicate that accepts some inputs the specification rejects (§3.3). C is compiled as a leaf function, and an object that references the global offset table is rejected (Report 4, §3.4).
  5. Ratios are against gcc -O2 on the reference C. The -Os size ratios (0.691 and 0.670) compare gcc -Os on the model's C with gcc -O2 on the reference, so most of the saving is the flag. Ratios are means over passing tasks only and are dominated by a few tasks (Tables 4 and 5).
  6. The hybrid reuses round 3 outputs. For c-then-asm, the C halves are those generated in round 3; no new generation was done for Part B.
  7. Loop budgets are not matched. The assembly loops use k = 8, R = 3; the C loop uses k = 4, R = 2. The c-then-asm loop ran in two sessions with the same settings, and the last 19 tasks were run after a restart.
  8. Failure buckets are harness labels. Part D maps the stored harness categories to buckets; it did not trace each failure by hand. "logic_mismatch" means the assembly ran and returned a wrong value; the two examples in §5 are read by hand, the rest are not. A zero abi count means the harness flagged no calling-convention violation, not that every crash is unrelated to register use.
  9. Tallies computed for this report. The pass-set overlaps between the two 7B models, the -O2/-Os pass-set check, Tables 4 and 5, the per-model loop counts on the 19 tasks, and the loop-against-C-pass counts are tallies of hybrid.jsonl and the loop.jsonl files, not figures in the summaries.
  10. Other. The pytest suite was not re-run for this report, and the human check of a sample of rewritten specifications is still outstanding (Reports 1 to 4).

9Proposed next steps updated 21 Nov 2026

proposed None of the following has been started. Each is a proposal for discussion, and none is a commitment.

  1. Adopt the hybrid as the practical system and baseline. Report "model C, gcc lowers it" as the system result (48/78 greedy held-out) and measure every assembly-writing approach against it on correctness first, then on size and instruction count.
  2. A model-C, gcc and repair loop. Run the repair loop on the C path: the model writes C, gcc compiles it, the visible tests give feedback, and the model revises the C. The 1.5B C loop already reaches 44/78; the fine-tuned 7B starts from 48/78 greedy, so this measures the ceiling of the C route with a matched budget.
  3. Distillation: train the assembly on gcc's lowering of the model's own C. For each training task, take the C the model actually writes (when it passes), compile it with gcc, and train the assembly half to reproduce that lowering. This targets the gap in §5 directly: the model would learn to lower the program it wrote, rather than to produce gcc output for the reference C.
  4. Differential testing against the model's own C inside the loop. When the model writes both halves, run the assembly against the compiled C on generated inputs as well as on the visible tests, and feed back the first disagreement. Part D shows that most failures are semantic mismatches with the C, which such a check can find without the hidden tests.
  5. A superoptimization pass on gcc's output. Start from the hybrid's gcc code, let the model (or a search) propose smaller or faster variants for the stated goal, and keep a variant only if it passes the tests and agrees with the original on generated inputs. The floor stays at the hybrid's pass rate; the question is how often it can beat gcc.
  6. Close the size and fine-tuning confound: run the untrained 7B in C mode, and a fine-tuned 1.5B in C mode, on the same held-out set.
  7. Better algorithms in the C. Where the hybrid is slow (Table 4), the cause is the algorithm. Training data or prompts that favor the reference algorithm, or a goal-aware C step, would address this before lowering.
  8. Stronger evaluation: a larger or fresher held-out set with confidence intervals, repeated seeds for the headline rows, and tests that catch weak predicates such as the he75_is_multiply_prime case.
